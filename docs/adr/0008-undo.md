# ADR-0008: Undo is a log of inverse commands, not a journal of row images

**Status**: accepted
**Date**: 2026-08-23

## Context

The register needs undo. Unlike almost everything else in this project, there is no rule to
measure: the reference application's undo is a property of its user interface, and its public API
exposes no undo endpoint, so the oracle has nothing to say about it. This is a design decision we
own, and it is recorded here rather than discovered in `docs/behavior/`.

Two shapes were considered.

**A journal of row images.** Record every row a command touches, before and after; undo restores
the "before" image. It covers every command automatically, including ones nobody thought about.

**A log of inverse commands.** Each mutation registers the command that undoes it; undo runs that
command through the ordinary path. It covers only what someone has written an inverse for.

## Decision

A log of inverse commands.

Restoring row images means writing to the ledger behind the commands' backs. Every invariant the
command layer enforces — that both legs of a transfer move together, that a credit-card payment
category exists exactly when its account does, that the recompute watermark moves back far enough
— would have to be re-derived by the undo path, or silently skipped. Undo would become a second,
weaker way to write to the database, and the first time the two disagreed the symptom would be a
budget that does not add up, discovered weeks later.

The inverse-command design has one real cost: a command with no registered inverse cannot be
undone. That cost is *visible*. The undo control knows what it can undo because the entry exists;
it can say so, and the absence shows up as a missing entry rather than as a restore that quietly
did half the job.

Inverses are registered inside `withPlanWrite`, in the same database transaction as the change
they invert, so an entry cannot outlive a rolled-back write or be lost by one.

## Scope

- **Per plan and per user.** Undo acts on your own last change. On a shared plan, one person's
  Ctrl-Z reaching into another person's work is a surprise no amount of labelling fixes.
- **Grouped.** One user action is one undo step, even when it performs many writes — deleting
  eleven selected rows undoes as one step, not eleven.
- **Redo is the forward command.** Performing anything new clears the redo stack for that user
  and plan, which is the behaviour every editor has trained people to expect.
- **Not durable across a restore.** Undo entries live in the database and travel with a backup,
  but restoring an older backup does not attempt to reconcile a newer undo stack against it; the
  stack is truncated to the restored state.

## Consequences

v1 registers inverses for creating, updating and deleting transactions, and for the bulk actions
built on them. Reconciliation is deliberately not undoable yet: its inverse has to un-reconcile a
set of rows *and* remove an adjustment, and getting that half-right is worse than not offering it.
The control says so rather than presenting a step that does nothing. See
`docs/behavior/divergences.md` D10.
