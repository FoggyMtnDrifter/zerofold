# Deliberate divergences from YNAB

Silent divergence is a bug. Every intentional difference is recorded here with its rationale.

| # | Area | YNAB | Zerofold | Rationale | Source |
|---|------|------|----------|-----------|--------|
| D1 | Transaction date lower bound | Rejects dates more than ~5 years old | No lower bound | Importing a decade of history from another tool is a first-class use case for a self-hosted app; our importers must not choke on it | [ADR-0007](../adr/0007-no-future-dated-transactions.md) |
| D2 | Target storage | One mutable goal per category | Revisions with `effective_from_month` | Makes a past month's "needed" reproducible, which the golden-file tests depend on. The compat API projects the revision effective at the requested month, so clients see no difference | plan §3 |
| D3 | Scheduled transactions | No end conditions or per-occurrence edits in the API | `end_date`, `end_after_occurrences`, and `scheduled_transaction_exception` exposed as documented extensions | The capabilities exist in YNAB's UI but not its API; hiding them from our own API would be an arbitrary limitation | plan §3 |
| D5 | Resolving "today" | Derives it from **UTC** — a starting balance created at 02:50 UTC on 2026-08-23 was dated 08/23 for a user whose local date was 08/22 | Resolve through the plan's IANA timezone | A transaction dated tomorrow is a bug from the user's point of view, and precisely the failure the calendar-date rule exists to prevent | [P0-C](P0-C-scheduled-accounts-deletion.md) |
| D6 | Deleting an account | Executes immediately on one click, destroying the account and its transactions | `AlertDialog` requiring the account name to be typed, plus an `audit_event` | Losing financial history to a misclick is indefensible in a tool whose promise is data ownership | [P0-C](P0-C-scheduled-accounts-deletion.md) |
| D7 | Closing an account | No "Close" control exists in the account UI at any balance; only Delete (R66) | Closing is a first-class operation, separate from deletion | Offering only deletion pushes people toward discarding financial history in order to tidy a sidebar. Closing keeps the history and the net-worth contribution | [P0-C](P0-C-scheduled-accounts-deletion.md) |
| D8 | Zero-balance starting transaction | Always writes a starting balance transaction, even for $0.00 | Written only when the opening balance is non-zero | A $0.00 row conveys nothing and clutters an empty register. Revisit if any import or reconciliation path turns out to depend on an origin row existing | [P0-C](P0-C-scheduled-accounts-deletion.md) |
| D9 | Editing a reconciled transaction | Reconciled rows can be edited like any other | Refused unless the caller passes `force`, with an error explaining the consequence | Reconciliation asserts that a set of rows matches a statement (R56). Editing one silently invalidates that assertion, and the user finds out at the next reconciliation when the numbers disagree and nothing records why. Still permitted — it is their data — but deliberate | R71 |
| D4 | Transfer pairing | Two rows linked by mutual `transfer_transaction_id` | Same, plus a `transfer_pair_id` identical on both legs | Avoids a circular FK (and the Postgres-only `DEFERRABLE` needed to express it) and makes "fetch the other leg" a single indexed lookup | plan §3 |
